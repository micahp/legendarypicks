The user-facing architecture is intentionally split:

1. Scheduled ingestion contacts UFCStats, archives bounded source responses, and
   writes normalized history to SQLite.
2. Opening **Last 5 fights** lazily calls the local API.
3. That API performs a read-only database query. It does **not** contact
   UFCStats or ESPN and does not write anything on the request path.

The data acquisition is therefore not lazy. Only the inexpensive local display
query is deferred until the user opens the form.

## 2. Why UFCStats was added

The current UFC board had numeric props for `significant_strikes` and
`fight_time`, but the existing ESPN history was stale and did not link to the
current fighters:

- August 29 board: 65 distinct line/provider significant-strike offers, 130
  side rows, and 20 players.
- August 29 board: 20 fight-time offers, 40 side rows, and 13 players.
- Union of current numeric-market fighters: 22.
- Existing ESPN UFC logs: 78; newest date 2026-07-18; current linked fighters: 0.
- Existing settled rows for those current numeric markets: 0.
- Initial database `PRAGMA quick_check`: `ok`.

UFCStats was selected because its completed-event pages and fighter profiles
publish the required historical facts: opponent, result, event/date,
significant strikes, method, round, and elapsed round clock. Total fight time is
derived with the same semantics as the old ESPN logs:

```text
(round - 1) * 300 + elapsed round clock
```

Direct requests encounter UFCStats' proof-of-work browser challenge. The new
stdlib client solves that challenge serially with explicit work/response bounds,
paces requests, caps responses at 2 MB, and stores gzip archives for reuse. The
completed-events page exposed 786 events; the August 29 card exposed 13 fights.

## 8. Holes and operational boundaries

### Production remains intentionally incomplete

Production does not have the UFCStats migration or backfill and was not tested
through this new production code path. A production rollout still requires a
separate authorization and must include, in order:

1. verify the absolute production database path and current service revision;
2. take and verify a SQLite API backup;
3. deploy compatible code and apply migration `20260829_001_ufcstats_game_logs`;
4. ingest exact current/completed targets serially from durable archives;
5. verify identities, counts, idempotency, API/UI visibility, settlement, and
   database integrity;
6. only then restart or alter production services if separately authorized.

The existing UFC fight-stats production timer was not restarted, enabled,
disabled, or otherwise changed. The updated runner has a migration gate and
should fail safely if invoked against an unmigrated production database, but it
must not be treated as deployed merely because the local source changed.

### Archives need an operational home

The source responses used today live in the ignored isolated-worktree archive
path. Before production use, copy or recollect them into the approved durable
operational archive location. Do not depend on an expendable feature worktree.
