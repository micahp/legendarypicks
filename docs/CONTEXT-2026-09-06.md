**Make `published_roster` hold every publisher that names a league's players,

Why it is the next thing rather than a nice-to-have: today I hand-wrote six

- **FotMob publishes exactly one spelling per player.** `playerData?id=652955`

  harder can never produce `Lobzhanidze`.
- **mlssoccer.com publishes both, on one page.** Its Sporting KC page displays
  "Jake Davis" and its own profile URL is `/players/jacob-davis/`. Likewise
  `/players/vitor-costa-de-brito/` displaying "Vítor Costa", and
  `/players/willy-kumado/` where ESPN files William.

**Every one of the six manual aliases is a pair MLS itself already prints.** The
alias table is not a judgment problem, it is the symptom of reading one
publisher when a second publishes the variance for free. That is
`feedback_we_systematically_underread_publishers` in its purest form.

The shape to build:

1. `_PROVIDERS` in `backend/ingest_published_rosters.py` is keyed league ->
   ONE provider. It should be league -> a LIST. `source` is already part of the
   table's primary key, so `published_roster` supports multiple publishers per
   league with no migration.
2. `published_roster.lookup` currently resolves only when exactly one row
   matches a folded name. With two publishers loaded, the SAME person matches
   twice, and today's uniqueness rule would read that as ambiguous and refuse.
   Two rows that are one person must collapse before uniqueness is judged.
   There is no shared id between FotMob and MLS to collapse on, so the join is
   (league, club, folded name) with the publisher ids kept side by side; get
   this wrong and the fix makes resolution WORSE than it is today. Write the
   test that loads two publishers for one squad before writing the ingest.
3. Then delete from `REVIEWED_ALIASES` every line the second publisher now
   reaches, and keep only what survives: genuine disagreement between two
   publishers about who someone is. If nothing survives, delete the table.

Do not skip 2 for 1 and 3. A second publisher loaded without the collapse rule
turns 895 resolvable MLS names into ambiguity.

**Then cut v0.9.3.** `CHANGELOG.md` has an uncommitted v0.9.3 section written

## The one thing to carry forward

**A name that does not resolve is a question about which publisher we asked, not
about the name.** Every strand of today converged on that. The resolver dropped
props for players FotMob had published all along. The audit failed on positions
FotMob had published all along. And the six names FotMob genuinely could not
answer, MLS answers on the same page as the first spelling. Not once today was
the answer "this data does not exist".

## 1. The resolver gave up 873,559 times

`_resolve_player_for_ingest` had four steps and then wrote the name to
`unresolved_players`. Giving up beats minting a shadow row, which is what it
replaced, but it means every prop for that person is dropped. Measured on prod:

| source | names | attempts |
|---|---|---|
| bovada | 1,254 | 873,559 |
| statcast | 398 | 13,823 |
| underdog | 228 | 5,641 |
| espn_roster | 254 | 403 |
| nhle.com | 204 | 395 |
| rotowire | 195 | 620 |

Two things that settles. It is **not** a sportsbook-vocabulary problem:
`espn_roster` itself fails on 254 names, so the spine is missing people ESPN's
own feed names. And 873,559 Bovada attempts are the same names retried every
thirty minutes for months, because the queue records a miss and nothing acts on
it.

So: a fifth step that reads the roster the publisher already published, and
creates the player already carrying their id and position. The opposite of a
shadow row. It READS A TABLE and never fetches, because it runs inside
`/api/props/ingest` and a serving path must not wait on a publisher.

Recovery measured against the existing queue:

```
mls     464 queued names -> 290 resolvable (62%),  3,764 of 5,925 attempts
lcup    199              -> 155 (78%),             4,107 of 6,215
ligamx   50              ->  22 (44%),             2,507 of 9,638
```

**Forward-fill, not backfill.** Micah's framing, and it is the right one: the
repair is that the next ingest resolves, not that a script patches what the last
one missed.

### Two corrections inside that work, both worth keeping

The first `fold` turned punctuation into a SPACE, so `Djé D'Avilla`,
`Dje DAvilla` and `Dje D\`Avilla` became three keys, which is exactly the
variance a sportsbook produces. It now squashes everything but the letters.
Uniqueness still decides.

A created row stored the SPORTSBOOK's spelling. We resolve BY the publisher's
identity, so their rendering is the fact and the book's is a display artifact.
Caught by Micah asking "the squashing doesn't mess up display names right".
`published_roster` stores `name` and `name_folded` separately; folding is only
ever a lookup key and never reaches a stored name.

## 3. spine_merge could not see a duplicate whose names differ

Binding those seven surfaced five collisions: each already existed a SECOND time
under the publisher's spelling, one row carrying an espn_id and 21-37 game logs,
the other carrying the sportsbook's name and the props. `spine_merge` groups by
exact name, and `Willy Kumado` never equals `William Kumado`.

Candidates now come from two sources feeding one keep/drop path. The second asks
which published squad member each row resolves to and groups the rows that
answer the same. **That is stricter than matching names, not looser.**

Three rules the published pass needs that the name pass does not:

- **Two rows carrying ids are not two people here.** The name pass refuses that
  case correctly, but these rows are grouped BECAUSE the publisher named them as
  one squad member, and an espn_id on one with a fotmob id on the other says
  nothing about either. Two different keys from the SAME publisher would say
  something, so that is the refusal.
- **The survivor is the row spelled the way the publisher spells it.**
- **`apply_plan` carries publisher ids onto the survivor before any delete, and
  clears them from the dropped row.** Without that the delete guard (which
  refuses to remove a row still holding an espn_id) would move every reference
  and leave an empty duplicate standing. The guard is right and stays.

Applied: 9 rows merged / 69 references moved on prod, 6 / 86 on dev.
