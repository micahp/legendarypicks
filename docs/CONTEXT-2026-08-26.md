## 1. THE SHAPE: a measurement is a claim about the INSTRUMENT

Eight false facts about publishers were written down in one session. Each was a
correct measurement of the wrong thing, and each would have read as settled to
whoever came next.

| written down | what was actually measured |
|---|---|
| "`sot` has 0 MLS log rows" | a lookup through the *ligamx* map, which has no `sot` entry — 0 by construction. The key is on 21,177 rows |
| "607 projections have no game link" | team-abbreviation matching. The games were linked; the abbreviations were absent |
| "RotoWire's soccer stops at MLS" | our own `LEAGUES` dict, which asks for four leagues |
| "only PrizePicks prices goalie saves" | one day of the relay. Saves appear on all 8 archived days, 142 props |
| "tackles/clearances/crosses are FotMob-only" | which provider we had looked at |

| "the relay republishes almost none of it" | 22 props on one fixture, one day |

Codified in three places, because one is where it gets missed:
`.claude/skills/measurement-is-a-claim`, a pointer in `docs/DEV-STANDARDS.md`,
and `feedback_measurement_is_a_claim` in memory. Commit `27ef294`.

**The rule that would have caught the most: ask a second way, and when two
answers disagree, the disagreement IS the finding.** `sot` returned 0 through one

**The most expensive one is not in the table.** `first_goal_scorer` was mapped to

1. **MERGE** FotMob into the ESPN row → FotMob tackles on a row stamped
   `source='espn'`. Provenance destroyed.
2. **A separate ROW in one table** → 2,619 appearances on dev and 2,538 on prod

   providers "separate", I built rows instead of tables.
3. **A separate TABLE** (`7634c6f`). `player_game_logs` is ESPN's again at one
   row per appearance; `player_game_logs_fotmob` is FotMob's; the view
   `player_game_logs_all` joins them so a value's provenance is the COLUMN it
   came from. A third provider is a third table, not a migration.

Applied to both databases behind verified backups. **The API response is
byte-identical**, so the frontend was untouched — a requirement, not a hope.

`test_spine_merge`'s schema pin caught it and asked exactly what it exists to
ask: should the spine merge reach the new table? Yes.

**I created the hazard this repo has a rule against**: prod's DATABASE was
migrated before prod's CODE. For a few minutes prod served old code against a new
schema. Caught at commit time, not by a check. Order is code first, then data.

## 4. Confidence: a second sort, because a percentage discards the sample

Sorting a Leagues Cup board by hit rate put a 3-game player first. 3/3 is
consistent with a true rate of 43.8%..100%; 28/48 with 44.3%..71.2%. Ranking
those by raw rate ranks luck above evidence.

`Confidence` (Wilson lower bound, 95%, over every game held) is added ALONGSIDE
hit rate, not replacing it, so the chip a reader sees and the order they chose
still agree. It needs no minimum-games threshold — which matters, because only
**3 of ~394** Liga MX players reach 10 appearances.

**The confusion it creates, unresolved and worth deciding:** the three chips are
WINDOWS and Confidence is the whole season, so it can land above or below them
with no visible reason. Naylor reads L20 75% / Confidence 70% (season 79%);
Alonso L20 70% / Confidence 49% (season 59%); Alvarez L20 45% / Confidence 53%
(season 63%, on a cold streak). **The number that explains it — the season rate —
is nowhere on the card.** Proposal on the table: render `Season 63% · Confidence
53%`. Open question: should Confidence follow the L5/L10/L20 toggle instead?

Also: a window short of its own sample now renders a DASH, on both the board
chips and the chart headline (`7498767`). L5/L10/L20 all printed 100% for a
three-game player.

## 6. The foreign keys were declared and had never fired

`props.player_id`, `props.game_id` and `prop_results.prop_id` have all DECLARED
their references since the schema was written. **SQLite defaults `foreign_keys`
OFF, per connection**, and only three scripts in the repo set it — not the API,
not settlement. A constraint that reads as protection in the schema and enforces
nothing is worse than none, because it stops anyone looking.

What it cost: the 78 props and the 4 orphaned results in §5. Nothing raised.

Both databases are now at **zero** `PRAGMA foreign_key_check` violations, and
`PRAGMA foreign_keys=ON` is set in `_core._db()` — the helper 70 non-test modules
import. Five tests assert it fires, including that an unresolved prop with
`player_id IS NULL` still writes, since NULL is the fail-closed path the
resolvers depend on.
