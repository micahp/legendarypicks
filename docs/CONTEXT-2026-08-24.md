## 13. Tennis: the cache-key collapse is REFUTED

The proposal was to key the tennis cache on the tournament rather than the date,
on the theory that ESPN ignores `?dates=` and returns the whole tournament anyway.
Seven paced probes:

```
date        events  matches  tournaments
2026-08-20     1      324    Cincinnati
2026-08-23     2      398    Cincinnati + Winston-Salem
2026-08-24     2      699    Winston-Salem + US Open
2026-08-26     2      699    identical match id set to 08-24
2026-09-02     1      625    US Open only
```

`?dates=` is **not** ignored. ESPN returns the tournaments whose window covers the
requested date, and the window moves. 08-24 and 08-26 do return an identical match
set, so duplication is real *inside* a tournament week. But no anchor is safe:
anchoring on the earliest date in a +/-1 day window loses 625 US Open matches at
the 08-23 to 08-25 boundary, anchoring on the latest loses Cincinnati and
Winston-Salem. All three variants would silently serve the wrong matches.

**There is no cheap key to collapse onto.** The payload's own calendar is
`calendarType: day`, 259 flat date scalars, no tournament boundaries. This is the
`day` calendar limit already recorded in `reference_espn_publishes_league_calendar`:
a `day` calendar can never say no.

What did work: `TENNIS_LIVE_TTL = 90` for atp/wta, 90 specifically because the live
timer fires at 60s and any window shorter than the tick guarantees the next tick
re-asks for a body it already holds. Uncached tennis per active minute 4.26 -> 2.80.
Two guards: an explicit caller wins so this moves the DEFAULT only, and `ttl=0` is
never widened, because 0 means "do not serve me a cached body" and widening it
would hand a verification probe a stale answer.

## 14. We polled tomorrow forever. 8 requests per run -> 1.

The largest single saving of the day, found while checking whether the tennis
+/-1 day window was earning anything. It was not the tennis window. It was every
league.

`needs_refresh` decided whether to spend a request by asking "is every game
final?". On a **future** date nothing is final, because nothing has started, so
the answer was always ask again. Every 10 minutes, all day, for a schedule that
cannot change.

```
league  date        ask?   reason           state
atp     2026-08-25  True   32 not final     32 pre, 0 in, 0 final
wta     2026-08-25  True   32 not final
mlb     2026-08-25  True   15 not final
ufc     2026-08-25  True    5 not final
lcup    2026-08-25  True    2 not final
```

**The asymmetry is what makes it a defect rather than a cost:**

```
nfl  2026-08-25  False  published no games 12m ago   <- empty:     3h backoff
mlb  2026-08-25  True   15 not final                 <- populated: no backoff
```

A league that published **nothing** for tomorrow was backed off. A league that
published a schedule was asked 144 times a day. The more a publisher told us, the
more we asked it.

`FUTURE_BACKOFF = 1h`. Two guards: any game already `in` or `post` overrides the
date entirely, because `game_date` is a slate day and the league clock can roll
over mid-game so a date comparison alone would park a live board; and `_today_for`
is asked for the date because tennis buckets by UTC and every other league by ET,
which is the same two-clock bug the empty backoff already had once.

This also removes an ESPN call from the **serving path**:
`routers/games/scoreboard.py:95` reads `needs_refresh` to decide whether a page
load falls through to the publisher, and that path took 13 of today's refusals.

         skip atp 2026-08-25: future slate, none started, asked 39m ago

And verified it is a saving rather than data loss. Tomorrow's board is intact,

### 16a. The regression I shipped in it, and caught an hour later

`spine_merge` defaulted to `data/picks.db` and **ignored `LP_DB_PATH`**, the
variable every other tool on this box is pointed with. It has `--apply`. So

```
LP_DB_PATH=data/picks.dev.db venv/bin/python spine_merge.py --apply
```

read as a dev rehearsal and would have merged rows in **PROD**. A destructive tool
must never resolve to prod through the same variable the operator used to say
"not prod".

The tell was in output I nearly took at face value: dev and prod both reported
447/225, for two databases whose duplicate counts differ (547 vs 293). Fixed to
honour `LP_DB_PATH`, with `--db` as the explicit override, and the resolved path
now printed **absolute and before anything is written**, because a relative path
in a log does not identify a database. Five tests, one deliberately end-to-end
through `main()` since the parser tests alone would still pass if `main()` built
its connection elsewhere, which is exactly the shape that hid this.
