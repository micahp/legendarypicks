## Root causes

### RC1. Identity from name and club alone

- `published_roster.py:555-561`: when a name matches a single player at the same club, the key
  binds to that player. Nothing else is checked. This is how 1259117 was bound on 2026-09-07:
  one LAFC player called Thayllon, so the key bound to him.
- `spine_merge.py:279-341` (`_unbound_binds`, d7810fc0): an unbound key binds when its name and
  club match a player who already holds any key from that publisher. This is how 1787871 was
  bound to New York's Ruiz on 2026-10-27. The rule treats "same publisher, same name, same club"
  as a double listing. Nothing checks birth date, ESPN id, career or the key's own games.
- `spine_merge.py:183-214` (`_published_groups`, via `published_roster.lookup`): name variants
  at one club become merges. This produced the Campagnolo merge (`Zackory` matched `Zack`).

### RC2. The conflict guard misses two keys inside one component

- `published_roster.py:619-624`: the conflict check compares each key with keys already bound to
  the player. It doesn't compare keys within the same component that are being bound in this run.
- Reproduced on a copy of the Oct 25 pre-run backup (`logs/roster_apply_thayllon_repro_copy.txt`):
  with both Thayllon keys unbound, one roster run bound 1259117 AND 1738398 to player 71244, in
  the same league. No refusal. That is the failure you were worried about: two people, one player.
- Live today: prod is safe for this pair only because 1738398 is bound, so 1259117 is refused.
  Any future state with two unbound keys of one publisher under one name would double-bind.

### RC3. Order decides who wins

- `published_roster.py:490-493`: components are sorted by `(priority, first key)`. For the
  Thayllon pair, 1259117 sorts before 1738398, so the wrong key is processed first and claims
  player 71244. The second key is then refused as a conflict against the first.

### RC4. Roster rows are never retired

- `ingest_published_rosters.py` has no DELETE. A player who leaves a squad keeps his last
  `(name, team)` claim forever. Prod: 78 of 3,433 roster rows were last refreshed before
  2026-10-26, including 1259117 (LAFC, since 09-27) and 1787871 (RBNY, since 09-07).
- Those stale claims are then used as evidence by RC1 and RC5.

### RC5. Self-confirming evidence

- `spine_merge.py:216-229` (`_roster_claims`): a player's claimed `(name, team)` pairs come from
  the roster rows already bound to that player. Each bind adds a claim, and the next bind is
  checked against it. A wrong bind therefore supports the next wrong bind.

### RC6. The review step could not see the evidence

- The spine_merge dry run prints names and counts only (`logs/spine_merge_dryrun_on_oct25_copy.txt`).
  It shows "BIND fotmob=1787871 ('David Ruiz') to player 58681" with no birth date, club history,
  ESPN id or game overlap. The 02:58 apply ran on that plan.
- The tests use invented keys (`F-MIA`, `F-NY`, `F1`). They cannot catch a wrong real-world bind.
- The repo contradicts itself: `published_roster.py` (about line 545) says the two David Ruiz
  records are "the concrete case" of two different people, and d7810fc0 merges them.
