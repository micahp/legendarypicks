## What went well

- **Foundation before features.** `player_game_logs` (the 111k-row spine) landed first; the
  player page, PropChart, matchups, and the game-page edge module all sit on top of it cheaply.
- **Disciplined fix ratio (14%)** and clean versioning — adopted semver mid-week, cut two tagged
  releases with changelogs. No fix-chains thrashing one subsystem.
- **Identity by ID, not name.** MLB dedup merges Statcast dup rows onto canonical; resolve-or-queue
  rule documented in AGENTS so the swarm follows it.

## Risks / findings

1. **Test ratio 0%.** Zero test files across 83 commits and 10.3k lines, on a codebase that now
   has a projection model, EV/CLV analytics, and identity-dedup logic — exactly the numeric/identity
   bugs that pass a visual check. The M7 audit caught "EV returns all zeros" by hand; a test would
   have caught it free. **Decision: very light tests deferred until after the entity-UX phases**
   (owner's call). When we do: cover `analytics/projections.py`, EV/CLV compute, identity resolution first.
2. **`backend/sports_service.py` god-file: 22 changes in one week**, more endpoints than the game page
   had components. **RESOLVED this session** — split into `_core.py` (DB/schema, helpers, market maps,
   models) + `routers/{games,players,props,analytics,game_extras}.py`; `sports_service.py` is now a thin
   app shell. 30 routes verified serving real data after the split.
3. **Docs at 31% of commits** (the largest category) — the swarm operating model showing up as resume
   handoffs + task specs + design docs. Real coordination overhead, not waste, but ~1 in 3 commits is
   planning, not code.
4. **83 commits / v0.2.1 sit on an undeployed branch.** The longer `analytics-backbone` stays unmerged
   from `dev`/prod, the scarier the eventual deploy.

## Habits for next week

1. When you write a numeric function, add one assertion in the same commit (under 5 min) — applies
   once the test-deferral lifts.
2. Before a multi-endpoint session, decide which router the new endpoint belongs in so the file
   structure stays clean by default.
3. Tag the deploy boundary in the resume doc when a feature is prod-ready, so merge-to-dev is a quick
   yes/no, not archaeology.
